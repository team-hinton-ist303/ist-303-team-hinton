# Sprint 2 retrospective: team responses

Answers to the three retro questions, sent by message around the [Nov 11 stand-up](2026-11-11-standup.md). These feed section 12 (Retrospective) of the README.

1. What went well?
2. What didn't go well?
3. How can we improve?

## Yalei Xu (Aaron), Nov 11

1. **Went well:** The early rendering spike helped us choose the right tools, and teammates supported each other through PR reviews and testing.
2. **Didn't go well:** Some PR reviews took longer than expected, merge conflicts caused delays, and some Sprint 2 tests depended on other features being merged first.
3. **Improve:** Review PRs within 24 hours, make task dependencies clearer in Jira, and plan future work based on our actual velocity.

## Ryan Miller, Nov 12

1. **Went well:** We delivered note entry, rests, sheet music, editing, deleting, settings and privacy. Tests grew from about 110 to 555 with 98% coverage, and GitHub now runs every test on every pull request.
2. **Didn't go well:** Many tasks depended on each other, so PRs piled up waiting on review or merge order, several of them conflicted with each other, and a few tasks finished late or got reassigned back and forth.
3. **Improve:** Agree on shared pieces like route names and fixtures before coding starts, keep PRs small and merge them in order, and assign a reviewer when the PR is opened so reviews start right away.

## Daniel Abalusi, Nov 12

1. **Went well:** We supported each other when tasks needed to be reassigned. Clear pull request reviews and automated tests helped us catch issues before merging. I also appreciated having a demo script and setup checklist to prepare for the presentation.
2. **Didn't go well:** Some tasks depended on unfinished features, so I couldn't complete the edit tests until the selection and edit form were merged. Keeping track of what was pushed, awaiting review, or merged was sometimes confusing.
3. **Improve:** Identify dependencies earlier, prioritize reviews that unblock teammates, and keep Jira updated with the PR link and current status. Preparing a shared demo environment earlier would also give us more time to rehearse.

## Beijia Gu (Jae), Nov 12

1. **Went well:** Teamwork and communication improved during Sprint 2. We helped each other through code reviews, and testing helped us catch bugs before merging. I also learned a lot from implementing features and reviewing other people's code.
2. **Didn't go well:** Some PR reviews and task dependencies caused delays. A few requirements also needed clarification during development, which led to extra changes and debugging.
3. **Improve:** We could clarify requirements and dependencies earlier, especially when multiple people are working on related features. Smaller PRs, faster reviews, and more frequent testing would also help us avoid last-minute issues.

## Varuzhan Shahidzadeh, Nov 12

1. **Went well:** Communication improved even more. The automated tests on every PR, although added late, helped speed up reviews.
2. **Didn't go well:** Some PRs still took days to be reviewed and approved, especially doc-only ones. Our scope grew near the end, which shows as a spike in the burndown, because we had a few tasks we hadn't added to the sprint. There were conflicts when merging, but they were easily resolved.
3. **Improve:** We could have automated the testing sooner, and reviewed and approved PRs sooner to prevent conflicts.
